# User Checkpoint -- Leader Brief

Use this pause state when Work genuinely requires user participation before the leader routes the user-approved continuation. The assigned worker then resumes the current quest in Work to apply that routing.

Leader actions:
- Keep the board row in `USER_CHECKPOINTING`.
- Include the exact assignee brief path in the instruction when asking an assignee to prepare the checkpoint packet: `~/.companion/quest-journey-phases/user-checkpoint/assignee.md`.
- Apply the `leader-decision-communication` skill before drafting or publishing. It owns the complete decision-first, plain-language, and necessity-filter rule; this brief owns checkpoint-specific approval, notification, and board mechanics.
- Present a self-contained user-facing checkpoint in the quest thread or main thread as appropriate. It must include findings, each named option, key tradeoffs, a recommendation, and the exact requested answer that will unblock the Journey. Use internally consistent, human-readable option labels, keep supporting technical evidence in the phase note, and reference the exact durable packet when approval binds to it.
- For a design decision, apply the authoritative continuation rule in `takode-orchestration/quest-journey.md`. The visible checkpoint must say whether each choice authorizes same-quest implementation, design-only closure, or a separate implementation successor; do not silently default to design-only closure.
- When notification shortcuts or answer options will be offered, publish a visible decision section before calling `takode notify`. Every shortcut option must be named and explained there with its meaning and relevant tradeoff; phase notes, private packets, notification summaries, labels/buttons, and "see feedback" references do not substitute. The section may be concise, but it must let the user choose each shortcut without opening hidden context.
- Treat the visible checkpoint prompt as the decision surface. Quest feedback, notification summaries, notification UI options, and `--suggest` choices are only attention/reply affordances; they must not be the only place options, tradeoffs, recommendations, or requested answers appear. A prompt that explains only **Fast A** while offering **Fast A**, **Careful B**, and **Pause C** shortcuts is incomplete until **Careful B** and **Pause C** are also explained in visible text.
- If two options are materially equivalent, either collapse them into one shortcut or name each and say there is no material tradeoff. For binary yes/no prompts, state what yes authorizes and what no declines or preserves. For multiple independent questions, show matching visible questions and use `--question` groups with the corresponding shortcuts. If free-form or custom answers are allowed, say what they mean; for exact approval-gated packets, an unlisted/custom answer is an edit or new alternative, not approval. For long packets, keep the evidence elsewhere but include a visible decision section with all option meanings before notify. For revised choices, resolve or supersede stale notifications, publish the revised visible section, and create a fresh notification.
- If the checkpoint includes worker/reviewer-originated relative paths or relative `file:` links for unported worktree state, resolve them before publishing with `takode file-resolve --session <worker-or-reviewer> <path-or-file-link>` and show the returned absolute `file:` link. Repo-relative links remain appropriate after Port/main sync or when intentionally pointing at the leader/main checkout.
- Do not use User Checkpoint to hand tracked work to a user before Work's required self-review and verification, or any independently authorized review, merely because the user wants to commit locally. Treat that as commit ownership, not an evidence waiver. Preserve explicit user overrides that actually change review requirements.
- Record User Checkpoint decisions as checkpoint decisions, not final `User review checks`. Only final Memory should settle post-completion checks after all agent-owned evidence is complete.
- Before entering a required checkpoint, or an optional checkpoint that will be taken, verify the approved suffix continues to a later Work occurrence before Memory. If it does not, revise the remaining Journey to `[user-checkpoint, work, memory]` before setting `USER_CHECKPOINTING`; a taken checkpoint must never advance directly to Memory.
- If an approved optional suffix is `[work, user-checkpoint, memory]` and Work proves its concrete skip condition, do not enter this pause. The worker uses guarded `takode board work-to-memory ... --skip-optional-checkpoint "<reason>"`, which records the skip reason while preserving the code-evidence boundary. Generic `board advance --skip-optional-checkpoint` must not be used when the destination would be Memory.
- After the self-contained user-visible checkpoint exists, call `takode notify needs-input` with a short summary. When it returns a notification id, immediately link the active board row to that user wait with `takode board set <quest-id> --status USER_CHECKPOINTING --wait-for-input <id>`, then wait for the user answer. Do not rely only on thread status markers, the notification list, or notification suggestions to represent a quest-blocking User Checkpoint wait.
- For externally consequential Work, a material edit alone is not approval. One fresh reply may make one exact substitution and explicitly approve the resulting packet only when the packet referent, every unchanged term, all dependent parameters, monitor/stop conditions, safety implications, consequences, and tradeoffs remain unchanged and unambiguous, and no question or user choice remains. For example, "Change the batch limit to 120" is edit-only, while "Approve the bounded operation with batch limit 120" is edit-plus-approval when all other packet terms still satisfy those conditions. Fail closed for edit-only replies, questions, vague/conditional/conflicting approval, ambiguous referents, dependent changes, changed monitor/stop conditions, changed safety implications/consequences/tradeoffs, or any remaining user choice: publish the revised exact packet, keep the board in `USER_CHECKPOINTING`, and wait for fresh explicit approval before external consequences.
- Harmless typo-only corrections can be recorded and allowed to proceed when the user explicitly approved the exact action and no approval ambiguity remains.
- Before resuming from `USER_CHECKPOINTING`, confirm that the user explicitly approved the exact resulting packet, any permitted exact substitution is incorporated, all fail-closed cases have instead been republished and reapproved, and no approval ambiguity remains. Record the scope and continuation decision and apply any approved scope change. When same-quest routing expands a previously design-only current quest to include implementation, reconcile the current quest metadata before clearing the wait or resuming Work: revise the title when it still reads as design-only, and update the description and TLDR when they no longer cover the full approved design-and-build scope. Do not defer this correction to final Memory. Update the remaining Journey only when the answer requires it, clear the linked wait, and return the current quest to its assigned worker in `WORKING`. Same-quest routing continues implementation; design-only or successor routing closes the current accepted scope before the guarded Work -> Memory transition.
- Require the assignee to add or refresh phase documentation before handoff when an assignee prepared the checkpoint. It should use phase-scoped quest feedback with full agent-oriented detail plus TLDR metadata when working on a quest, falling back to explicit `--phase user-checkpoint` if current-phase inference is unavailable.
- Provide only deltas the assignee is unlikely to infer from the phase brief, quest record, current artifacts, or their own context: exact accepted refs, unusual scope boundaries, nonstandard verification, safety warnings, or facts unavailable to that actor. Avoid restating generic closure checklists covered by the brief.
- Do not use this pause as terminal closure, a generic TBD bucket, or a leader-only indecision placeholder.
