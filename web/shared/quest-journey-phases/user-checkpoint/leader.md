# User Checkpoint -- Leader Brief

Use this pause state when Work genuinely requires user participation before the leader routes the user-approved continuation. The assigned worker then resumes the current quest in Work to apply that routing.

A quest is in User Checkpoint while the user has your open question about it: your `takode notify needs-input` in the quest's thread moves its Work into the planned checkpoint when one comes next, or into one Takode adds, and links the question. A checkpoint Takode added returns to Work by itself when its questions are resolved, and a new question within 10 minutes reopens it; a planned one resumes with `board advance`. The worker may keep gathering information or brainstorming meanwhile. Add `--no-checkpoint` for a question the work does not wait on, and end any checkpoint early with `takode board set <quest-id> --status WORKING`, which resumes the Work after it (its questions stay open, not blocking; clearing a question's link with `--clear-wait-for-input` never resolves it either). A planned checkpoint left that way while its questions are still open is not used up: Takode puts it back after the resumed Work. A `notification_dismissed` herd event tells you when the user dismissed a question without answering. The full rules are in Automatic User Checkpoints in `takode-orchestration/quest-journey.md`.

Leader actions:
- Keep the board row in `USER_CHECKPOINTING`.
- Include the exact assignee brief path in the instruction when asking an assignee to prepare the checkpoint packet: `~/.companion/quest-journey-phases/user-checkpoint/assignee.md`.
- Apply the `leader-decision-communication` skill before drafting or publishing. It owns the complete decision-first, plain-language, and necessity-filter rule; this brief owns checkpoint-specific approval, notification, and board mechanics.
- Present a self-contained user-facing checkpoint as the context of `takode notify needs-input` (`--context-file -`), with the exact requested answer as its `--question`, routed to the quest thread or main thread as appropriate. Takode shows the context in the thread as a normal message right before the question card; do not repeat it in chat, because text written before a tool call in the same response may never be shown. It must include findings, each named option, key tradeoffs, a recommendation, and the exact requested answer that will unblock the Journey. Use internally consistent, human-readable option labels, keep supporting technical evidence in the phase note, and reference the exact durable packet when approval binds to it.
- For a design decision, apply the authoritative continuation rule in `takode-orchestration/quest-journey.md`. The checkpoint must say whether each choice authorizes same-quest implementation, design-only closure, or a separate implementation successor; do not silently default to design-only closure.
- When notification shortcuts or answer options will be offered, the context must let the user choose each one without opening hidden context. Explain there every option whose meaning or tradeoff is not obvious from its label and the question; self-explanatory options such as yes/no or **Approve** / **Change something** need no separate explanation. Phase notes, notification summaries, labels/buttons, and "see feedback" references do not substitute for a needed explanation.
- Treat the needs-input context and questions as the decision surface. Quest feedback, notification summaries, notification UI options, and `--suggest` choices are only attention/reply affordances; they must not be the only place options, tradeoffs, recommendations, or requested answers appear. A prompt that explains only **Fast A** while offering **Fast A**, **Careful B**, and **Pause C** shortcuts, whose tradeoffs the labels alone do not convey, is incomplete until **Careful B** and **Pause C** are also explained in the context.
- If two options are materially equivalent, either collapse them into one shortcut or name each and say there is no material tradeoff. For binary yes/no prompts, make clear what yes authorizes and what no declines or preserves; when the question already says so, do not restate it per option. For multiple independent questions, use `--question` groups with the corresponding shortcuts. If free-form or custom answers are allowed, say what they mean; for exact approval-gated packets, an unlisted/custom answer is an edit or new alternative, not approval. For long packets, keep the evidence elsewhere but include a decision section in the context that explains every option needing it. For revised choices, resolve or supersede stale notifications and create a fresh notification with the revised context.
- If the checkpoint includes worker/reviewer-originated relative paths or relative `file:` links for unported worktree state, resolve them before publishing with `takode file-resolve --session <worker-or-reviewer> <path-or-file-link>` and show the returned absolute `file:` link. Repo-relative links remain appropriate after Port/main sync or when intentionally pointing at the leader/main checkout.
- Do not use User Checkpoint to hand tracked work to a user before Work's required self-review and verification, or any independently authorized review, merely because the user wants to commit locally. Treat that as commit ownership, not an evidence waiver. Preserve explicit user overrides that actually change review requirements.
- Record User Checkpoint decisions as checkpoint decisions, not final `User review checks`. Only final Memory should settle post-completion checks after all agent-owned evidence is complete.
- Before entering a required checkpoint, or an optional checkpoint that will be taken, verify the approved suffix continues to a later Work occurrence before Memory. If it does not, revise the remaining Journey to `[user-checkpoint, work, memory]` before setting `USER_CHECKPOINTING`; a taken checkpoint must never advance directly to Memory.
- If an approved optional suffix is `[work, user-checkpoint, memory]` and Work proves its concrete skip condition, do not enter this pause. The worker uses guarded `takode board work-to-memory ... --skip-optional-checkpoint "<reason>"`, which records the skip reason while preserving the code-evidence boundary. Generic `board advance --skip-optional-checkpoint` must not be used when the destination would be Memory.
- Call `takode notify needs-input` in the quest's thread with a short summary, the checkpoint question, and the checkpoint packet as its context, then wait for the user answer. Takode links the question to the board row and enters the checkpoint; do not rely only on thread status markers, the notification list, or notification suggestions to represent a quest-blocking User Checkpoint wait.
- For externally consequential Work, a material edit alone is not approval. One fresh reply may make one exact substitution and explicitly approve the resulting packet only when the packet referent, every unchanged term, all dependent parameters, monitor/stop conditions, safety implications, consequences, and tradeoffs remain unchanged and unambiguous, and no question or user choice remains. For example, "Change the batch limit to 120" is edit-only, while "Approve the bounded operation with batch limit 120" is edit-plus-approval when all other packet terms still satisfy those conditions. Fail closed for edit-only replies, questions, vague/conditional/conflicting approval, ambiguous referents, dependent changes, changed monitor/stop conditions, changed safety implications/consequences/tradeoffs, or any remaining user choice: publish the revised exact packet, keep the board in `USER_CHECKPOINTING`, and wait for fresh explicit approval before external consequences.
- Harmless typo-only corrections can be recorded and allowed to proceed when the user explicitly approved the exact action and no approval ambiguity remains.
- Before letting the worker continue (Takode may already have returned a checkpoint it added to Work; resume a planned one with `board advance`), confirm that the user explicitly approved the exact resulting packet, any permitted exact substitution is incorporated, all fail-closed cases have instead been republished as a new question (which reopens the checkpoint) and reapproved, and no approval ambiguity remains. Record the scope and continuation decision and apply any approved scope change. When same-quest routing expands a previously design-only current quest to include implementation, reconcile the current quest metadata before the worker continues: revise the title when it still reads as design-only, and update the description and TLDR when they no longer cover the full approved design-and-build scope. Do not defer this correction to final Memory. Update the remaining Journey only when the answer requires it, and pass the continuation on to the assigned worker in `WORKING`. Same-quest routing continues implementation; design-only or successor routing closes the current accepted scope before the guarded Work -> Memory transition.
- When an assignee prepared the checkpoint, its brief already requires it to add or refresh phase documentation (phase-scoped quest feedback with full agent-oriented detail plus TLDR metadata) before handoff. Check that it exists rather than restating the duty in the instruction.
- Provide only deltas the assignee is unlikely to infer from the phase brief, quest record, current artifacts, or their own context: exact accepted refs, unusual scope boundaries, nonstandard verification, safety warnings, or facts unavailable to that actor. Avoid restating generic closure checklists covered by the brief.
- Do not leave a quest indefinitely active merely because its unresolved work might be revisited. When the user decides not to pursue further work, complete the normal closure flow, recording what was delivered and what remains unresolved without claiming full success. Preserve genuine temporary waits and explicit requests to keep a quest open; clarify once if “pause” is ambiguous.
